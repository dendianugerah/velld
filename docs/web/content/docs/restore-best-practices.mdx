title: Restore and recovery
description: Verify a backup, create a masked branch, rehearse upgrades, or recover to a timestamp.

## Restore to an empty database

1. Create a new, empty database of the same engine and add it as a separate [connection](/docs/databases).
2. In **Backup history**, open the completed backup, select **Restore**, and choose the new target. Confirm the destination before starting.
3. Check the restored data and run application smoke tests. For a production cutover, switch the application only after validation and retain a rollback path.

Manual restore is not a merge or a rollback button. Do not run it against your existing production database. A target may be partially populated after a failed restore; retry into a fresh target.

## Restore checks

With [Docker access](/docs/installation#enable-docker-features), completed PostgreSQL, MySQL, and MongoDB backups are restored into disposable containers, one at a time. D1 exports are checked in temporary SQLite without Docker. In **Backup history → backup → Overview**, open **Restore check output** for diagnostics. **Restore not checked** is not a pass. A passed check verifies the test restore, not application compatibility or the production target's roles and extensions.

## Create a masked branch

1. Open a completed PostgreSQL, MySQL, or MongoDB backup in **Backup history → backup → Branch**.
2. Copy its generated connection string and connect from the Docker host. The address uses `127.0.0.1`; a remote client needs a tunnel to that host.
3. Run tests on the copy. The branch expires after 24 hours; do not use it as persistent storage.

Velld masks values it recognizes before issuing credentials. This is not a guarantee that all sensitive data is removed. Review the copy before sharing it.

## Compare schemas

For a completed PostgreSQL or MySQL backup, select **Compare schema**. Compare it against another completed backup of the same engine or against the original connection's live database. Velld restores the backup into a disposable container to inspect its schema. The output is SQL from the source backup schema toward the chosen target schema, not a row diff. Review and test it separately; Velld does not apply it.

## Test on PG 18

Open a completed PostgreSQL backup and select **Test on PG 18**. The rehearsal restores the dump into a disposable PostgreSQL 18 container and reports restore diagnostics such as extension, role, and compatibility issues. Fix blockers, take a fresh backup, and test again. This doesn't change the source database or guarantee application compatibility.

## Safe upgrades

Use **Connections → connection → Recovery → Safe upgrades** for a database container that Velld can match on its Docker daemon. Choose a different supported image for that engine, such as `postgres:18` for a supported PostgreSQL container running `postgres:17`.

Plan downtime and stop application writes **before** the operation. It snapshots the database before stopping the original container, restores into a replacement, and checks container health plus object and record counts. If replacement or verification fails, Velld attempts to restart the original and reports whether rollback was verified. Check the result and smoke-test the application before resuming writes. Keep an independent backup; these checks don't prove the whole application or cluster was migrated.

## Point-in-time recovery

PITR uses a baseline and database logs, not the ordinary scheduled dumps. It supports PostgreSQL and MySQL. Set the connection's database name first.

- **PostgreSQL 13+:** Use a primary with WAL archiving enabled, no custom tablespaces, and credentials allowed to run `pg_basebackup`. Configure `archive_command` on the source to preserve the WAL files in the connection's own directory. Mount the archive root into the API and set `VELLD_PITR_WAL_DIR` to that mount. If it is `/wal`, Velld reads `/wal/<connection-id>`. Keep the segments needed from the baseline through your target.
- **MySQL:** Use InnoDB tables and uncompressed row-based binary logging (`log_bin=ON`, `binlog_format=ROW`, `binlog_transaction_compression=OFF`). Give the connection access to read binary logs and archive them before the source purges them.

Open **Connections → connection → Recovery → Point-in-time recovery**:

1. Choose **Create baseline**. For MySQL, use **Archive new logs** to extend coverage.
2. Choose a past local timestamp at or after the baseline. MySQL restores to before the selected second.
3. Choose **Restore copy**. Docker is required. The **unmasked** copy runs on the Docker host with temporary credentials and expires after 24 hours. The source is unchanged.

Baselines are stored under `.pitr` in Velld's local backups directory, separate from ordinary backup uploads.
